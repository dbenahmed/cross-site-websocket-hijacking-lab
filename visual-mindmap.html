Cross-Site WebSocket Hijacking (CSWSH)
Why an external tab can hijack a live WebSocket stream WITHOUT ever seeing the user's JWT token

A. Why the Vulnerability Exists

1. No Browser SOP on WebSockets Unlike fetch(), the browser's Same-Origin Policy does NOT block cross-origin new WebSocket() connections.
2. Raw Node.js ws Accepts All Origins By default, ws does not inspect req.headers.origin during the HTTP Upgrade handshake.
3. Ambient Cookie Attachment When Tab 2 opens ws://chat-server/chat, the browser automatically attaches the user's cookie for chat-server.
4. No Custom WS Headers in Browser Browser new WebSocket(url) does not allow custom Authorization: Bearer headers, pushing developers to use cookies.

B. What the External Page Can & Cannot Do

CANNOT Read document.cookie The JWT cookie is HttpOnly and scoped to the Chat Server. Tab 2 never sees the JWT token string!
CANNOT Read HTTP fetch() If Tab 2 calls fetch("http://chat-server/api/..."), the browser's Same-Origin Policy (CORS) blocks Tab 2 from reading the response.
CAN Hijack new WebSocket() If the server only checks the cookie, Tab 2 gets a live 2-way WebSocket pipe to read private messages and send forged ones!

C. Browser Rules: "Site" vs "Origin"

SITE (Controls SameSite Cookies) Checks scheme + root domain ONLY.
Ignores ports and subdomains!
• localhost:5000 & :3000 = Same Site
• blog.co.com & chat.co.com = Same Site
ORIGIN (Controls fetch SOP & Origin Header) Checks scheme + exact subdomain + exact port.
• localhost:5000 ≠ localhost:3000
• blog.co.com ≠ chat.co.com
Public Suffix List (PSL) Cloud domains like *.netlify.app, *.vercel.app, *.azurewebsites.net are treated as Different Sites.

D. Our Two Defenses (Mode 2 & Mode 3)

Defense 1: Strict Origin Validation Server checks req.headers.origin on the HTTP upgrade event against ALLOWED_ORIGINS. Rejects untrusted origins with 403 Forbidden.
Defense 2: Single-Use Ticket (15s TTL) WebSocket upgrade ignores cookies completely! Client must first call POST /api/ws-ticket (protected by Browser SOP) to get a 15-second UUID, which is burned immediately on first use.

3. Side-by-Side Comparison of the 3 Modes in Our Project

1. Vulnerable (Cookie Only) vulnerable

How it authenticates:
Reads req.headers.cookie during server.on('upgrade') and verifies the JWT.
Why it fails:
Completely ignores req.headers.origin. Any external tab whose browser attaches the cookie is upgraded (101 Switching Protocols).

2. Origin Validation origin

How it protects:
Checks config.ALLOWED_ORIGINS.includes(req.headers.origin) before upgrading.
Why it works:
The browser stamps the true Origin header (e.g. http://localhost:5000) and forbids JS from spoofing it. Server rejects with 403 Forbidden.

3. Origin + One-Time Ticket both

Step 1 (HTTP POST):
Client calls fetch('/api/ws-ticket') to get a 15s UUID. External origins are blocked by Browser SOP from reading this response!
Step 2 (WS Upgrade):
Server checks Origin AND requires ?ticket=<uuid> (ignoring cookies on WS), then immediately deletes the ticket from memory so it can never be reused.
